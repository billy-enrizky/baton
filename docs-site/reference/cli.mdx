Every interactive action has a command-line form for scripts and pipelines. Machine output stays on stdout and progress stays on stderr, so `--json` output can go straight into `jq`.

## Global flags

Global flags apply before or after a subcommand.

```sh
baton -C <dir>                    # working directory
baton -t <thread-id>              # target a thread
baton -p <provider> -m <model>    # harness and model overrides
baton --effort <level>            # reasoning effort where supported
baton --mode <single|orchestrate> # session mode for new work
baton --plan                      # read-only plan permission mode
baton --full-auto | --yolo        # accept edits, or bypass permissions
baton --limit <n>                 # list or output limit
baton --dry-run                   # inspect without running a turn
```

`--plan` is the read-only permission mode. `--plan-file` feeds a plan to orchestration. `/plan` shows the plan a harness reported, including markdown and file plans.

## Sessions and inspection

```sh
baton                              # fresh session
baton new [title]                  # start a thread
baton -t <id>                      # open a thread
baton login <provider>             # sign in to a harness
baton default <provider>           # set the default harness
baton threads [--json]
baton inbox [--json]
baton status [-t id] [--json]
baton activity [-t id] [--json]
baton turns [-t id] [--json]
baton agents -t <thread-id> [--json]
baton usage [--by day|model|provider] [--json]
baton search <query> [--all] [--json]
baton doctor [--json]
baton ps [--json]
baton serve [--stdio | --socket <path>]  # claim the store and serve the pipe or socket
# at the host terminal: pair [--label <name>] [--scope <s>]... [--ceiling <mode>] [--expires-days N]
baton attach --url <url> [--json]  # read a paired host's status over the socket
baton attach --url <url> --thread <id> [--messages] [--after N] [--limit N] [--follow] [--json]
baton attach --url <url> --thread <id> --submit <text> [--idempotency-key <key>] [--json]
baton attach --url <url> --approvals [--thread <id>] [--json]
baton attach --url <url> --respond <request> --choice <choice> [--idempotency-key <key>] [--json]
baton host takeover --pid <pid>    # replace a live host after confirmation
```

A directory with no threads is not an error. `baton status` exits 0 and reports `thread_id: null` with `next_action: "start a thread with baton"`.

`baton serve` claims the local store for one host process, runs provider and turn recovery, and listens on `BATON_HOME/serve.sock` with mode 0600 until SIGINT or SIGTERM. `--stdio` serves the spawner pipe instead, and `--socket <path>` overrides the path. On shutdown it stops recorded provider children with a verified command and start identity, cancels the turns, tasks, and runs it owns with the `host shut down` reason, reports the worktrees it leaves in place, settles turns and runs whose owner process stopped, then releases the claim. A second host is refused with exit code 3 and the owning process. While a host is live, CLI and MCP clients exit 4 and name the owning pid and takeover hint. The TUI opens read-only with the same notice.

`--stdio` accepts one newline-delimited JSON request per line. The response echoes `id`, and stdout carries protocol lines only:

```json
{"v":1,"kind":"request","id":7,"command":"status","args":{"thread":null}}
{"v":1,"kind":"response","id":7,"ok":true,"result":{"scope":"host","threads":2,"running_turns":0}}
```

| Command | Result |
| --- | --- |
| `ping` | `{"pong":true}` |
| `claim-info` | The live claim row, or `null`. |
| `status` | `{"scope":"host" or "thread","threads":n,"running_turns":n}` |
| `messages` | `{"thread_id":"...","cursor":n,"running_turns":n,"messages":[{"id":n,"turn":n,"role":"...","provider":"...","model":"...","text":"...","created_at":"..."}]}` |
| `submit` | `{"thread_id":"...","accepted":true}` on the first request; a repeat with the same `args.idempotency_key` returns the stored body with `"replayed":true`; requires the `operate` scope, a thread under the served project, a non-bypass thread, and a key of 1 to 128 characters |
| `approvals` | `{"approvals":[{"request_id":"...","thread_id":"...","kind":"...","summary":"...","choices":[{"id":"...","label":"...","kind":"..."}]}]}`; requires the `read` scope and accepts an optional `args.thread` filter |
| `respond` | `{"request_id":"...","thread_id":"...","choice":"...","decision":"...","answered":true}`; requires the `approve` scope and `args.idempotency_key`; a wrong or already answered request answers `not_found`, and a repeat returns the stored body with `"replayed":true` |

`submit`, `approvals`, and `respond` need the host engine and are available over the local socket; `--stdio` answers `ping`, `claim-info`, and `status` only. A malformed line or unsupported version answers with `id: null` and code `malformed_line` or `bad_version`, and the host continues. An unknown command answers `not_implemented`. EOF stops the host and releases the claim.

The pipe's authority is its spawner, so `--stdio` requests need no grant. Over the local socket, every request except `ping` also carries `grant_id` and `secret`. The host accepts only the same uid, verifies the grant, and requires the `read` scope for `claim-info`, `status`, and `messages`. `submit` requires the `operate` scope, and `respond` requires the `approve` scope. A missing grant answers `unauthenticated`, a refused grant answers `not_found`, `bad_secret`, `revoked`, or `expired`, and a granted command without the scope answers `not_permitted`. A different uid is closed with `peer_uid`. The socket is removed on shutdown.

`baton grant list` shows each grant's scopes, ceiling, expiry, state, and label, never its secret or hash. `baton grant renew <id> [--days N]` extends a live grant from now, keeps the later of the stored and requested instants, and leaves the secret file and hash untouched, so a connected client keeps working. It refuses a revoked grant and writes a `grant.renew` audit row. `baton grant revoke <id>` deletes the client secret file and refuses every later request with `revoked`. `baton audit list [--limit N] [--json]` shows the append-only audit log. Each event records the actor, environment, target, action, scope, confirmation, payload digest, result, timestamp, and retention. The target names what changed: a grant id for grants, a thread id for turns and MCP mutations, the provider request id for approvals and questions, the commit sha or pull request number for git actions. The table rejects updates and deletes, and a grant mint or revoke commits with its audit row in one transaction. Every accepted turn writes a `turn.submit` row in the same transaction as its message and turn rows; a refused or failed submission writes none, and the digest covers the thread, provider, model, and queue-drain flag, never the prompt text. Every approval answer writes an `approval.decide` row with actor `tui`, scope `approve`, the request id, the kind, the decision, and the chosen label before the provider receives it; if the row cannot be written, the provider receives a denial instead. Every question answer writes a `question.answer` row with actor `tui`, scope `approve`, the request id, the prompt count, and the chosen option labels; free-text answers are counted but never committed. If the row cannot be written, the provider receives empty answers. Successful git actions append `git.commit`, `git.push`, `git.pr`, `git.review`, or `git.merge` rows with actor `tui`, scope `git`, the thread id, and identifiers such as the commit sha, branch, pull request number, and merge method. A failed git command changes nothing and writes no row; when the row cannot be written after a successful action, the notice says so. Saving a global setting from `/settings` appends a `settings.write` row with actor `tui`, scope `settings`, and the setting key as the target; the digest covers the key and the new value, and a row that cannot be written is reported after the setting saves. Starting a run appends `orchestration.start` with scope `orchestrate`, and settling one appends `orchestration.settle` with scope `admin`, both with the run id as the target and in the same transaction as the run change, so a refused settlement writes no row. `baton memories add`, `remove`, and `clear` append `memory.add`, `memory.remove`, and `memory.clear` with actor `local_cli`, scope `settings`, and the memory id or scope as the target, in the same transaction as the memory change. MCP fork and queue clear also write audit rows, with the stdio spawner recorded as the confirming authority. At the host terminal, `pair [--label <name>] [--scope <s>]... [--ceiling <mode>] [--expires-days N]` mints a grant with `read` and `operate` by default and prints a `baton://local#...` URL whose fragment carries the secret. Add `--scope approve` when the client must answer approval requests. The ceiling is `default` unless you pass `--ceiling plan`, `default`, or `acceptEdits`; bypass is never grantable. `renew <id> [--days N]` extends one live grant from that terminal and works while the host holds the store. The URL is a credential, so keep it out of public logs. `baton attach --url <url> [--json]` sends one read-only `status` request over the socket and prints the host scope, thread count, and running turn count. `--thread <id>` reads that thread's status, `--messages` returns one page of its stored messages from a resume cursor, and `--follow` polls until the thread is idle so a client can watch a turn without the TUI. `--submit <text>` starts a turn on that thread through the host engine. The host serves the project directory it was started in: a thread outside it answers `wrong_project`, and a thread in `bypassPermissions` or above the grant ceiling answers `ceiling`. `--idempotency-key <key>` reuses a retry key, and attach makes a fresh one when the flag is absent. The first accepted request stores its result in the `idempotent_requests` table, and a repeat with the same key returns the stored body with `replayed` set and starts no second turn. A stored result is replayed for seven days; after that a retry starts a new turn. A raw socket `submit` must send `args.idempotency_key` as a non-empty string of at most 128 characters. `--approvals` lists pending approval requests, optionally filtered by `--thread`. `--respond <request> --choice <choice>` answers one with the `approve` scope and writes an `approval.decide` row named by the grant; a wrong or already answered request answers `not_found`, and a repeated key returns the stored answer with `replayed` set. The socket request writes a `turn.submit_request` audit row named by the grant before the engine starts, and the engine's own `turn.submit` row records the execution. The cursor is the last message id, so `--after <id>` resumes after a reconnect without repeating or skipping rows. Attach does not start a second engine or run recovery. The local socket and attach are available on macOS and Linux; Windows uses `baton serve --stdio`.

`baton host takeover --pid <pid>` prints the live claim's pid and process start and asks for a `y` or `yes` answer. Confirmation replaces the claim, fences the old host out, stops provider children recorded under the old host generation, settles all open turns and running orchestration, and releases the store for a new host. A wrong pid, changed claim, dead owner, held write lock, or declined prompt leaves the claim untouched. The old host process is not signalled.

## Turns and execution

```sh
baton exec -p <provider> [--effort level] [--json | --stream-json] "prompt"
baton exec -t <worker-thread> [--json] [--no-review] "answer"
baton spawn [-p provider] [--json] "task"
baton resume [-t id] [--fork] [--print] [--force]
baton fork [-t id] [--turn n] [--native] [--json] [title]
baton rewind [-t id] --turn N [--native] [--json]
```

`baton exec` runs one prompt and prints the result. `--stream-json` emits one JSON object per line, ending with a `type: "result"` row.

## Orchestration

```sh
baton orchestrate [--max-tasks N] [--plan-file path] [--plan-only] "goal"
baton orchestrate --list [--all] [--json]
baton orchestrate --run <run-id> [--json]
baton orchestrate --review <run-id> [--task N] [--json]
baton orchestrate --integrate <run-id> [--task N] [--json]
baton orchestrate --open-prs <run-id> [--task N] [--json]
baton orchestrate --archive <run-id> [--json]
baton runs settle <run-id> --status <status> [--force] [--json]
baton worktrees [--json] [--run <id>]
baton worktrees --clean [--force] [--run <id>]
```

`--max-tasks` accepts 1 to 16. `--integrate` merges approved worker branches. `--open-prs` pushes each approved branch and opens one pull request.

`baton runs settle` records a final status for a run that nothing is driving. Statuses are `completed`, `partial`, `failed`, `cancelled`, `needs_review`, and `needs_input`. `completed` is refused unless every task completed and no turn is open. Any other status closes open tasks and turns first. A run whose recorded owner is still alive needs `--force`.

## MCP

`baton mcp` serves the local store over MCP stdio.

```json
{
  "mcpServers": {
    "baton": {
      "command": "baton",
      "args": ["mcp"]
    }
  }
}
```

The server exposes 15 tools: `baton_doctor`, `baton_status`, `baton_threads`, `baton_turns`, `baton_agents`, `baton_messages`, `baton_queue`, `baton_search`, `baton_latest_diff`, `baton_processes`, `baton_orchestration_runs`, `baton_orchestration_report`, `baton_activity`, `baton_memories`, and `baton_fork`.

It is read-only except for `baton_queue` clear and `baton_fork`, which creates a new thread and leaves the source unchanged. The server reads the same database and honors `BATON_HOME`.
