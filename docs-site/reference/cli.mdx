Every interactive action has a command-line form for scripts and pipelines. Machine output stays on stdout and progress stays on stderr, so `--json` output can go straight into `jq`.

## Global flags

Global flags apply before or after a subcommand.

```sh
baton -C <dir>                    # working directory
baton -t <thread-id>              # target a thread
baton -p <provider> -m <model>    # harness and model overrides
baton --effort <level>            # reasoning effort where supported
baton --mode <single|orchestrate> # session mode for new work
baton --plan                      # read-only plan permission mode
baton --full-auto | --yolo        # accept edits, or bypass permissions
baton --limit <n>                 # list or output limit
baton --dry-run                   # inspect without running a turn
```

`--plan` is the read-only permission mode. `--plan-file` feeds a plan to orchestration. `/plan` shows the plan a harness reported, including markdown and file plans.

## Sessions and inspection

```sh
baton                              # fresh session
baton new [title]                  # start a thread
baton -t <id>                      # open a thread
baton login <provider>             # sign in to a harness
baton default <provider>           # set the default harness
baton threads [--json]
baton inbox [--json]
baton status [-t id] [--json]
baton activity [-t id] [--json]
baton turns [-t id] [--json]
baton agents -t <thread-id> [--json]
baton usage [--by day|model|provider] [--json]
baton search <query> [--all] [--json]
baton doctor [--json]
baton ps [--json]
baton serve [--stdio | --socket <path>]  # claim the store and serve the pipe or socket
# at the host terminal: pair [--label <name>] [--scope <s>]... [--expires-days N]
baton attach --url <url> [--json]  # read a paired host's status over the socket
baton host takeover --pid <pid>    # replace a live host after confirmation
```

A directory with no threads is not an error. `baton status` exits 0 and reports `thread_id: null` with `next_action: "start a thread with baton"`.

`baton serve` claims the local store for one host process, runs provider and turn recovery, and listens on `BATON_HOME/serve.sock` with mode 0600 until SIGINT or SIGTERM. `--stdio` serves the spawner pipe instead, and `--socket <path>` overrides the path. On shutdown it stops recorded provider children with a verified command and start identity, cancels the turns, tasks, and runs it owns with the `host shut down` reason, reports the worktrees it leaves in place, settles turns and runs whose owner process stopped, then releases the claim. A second host is refused with exit code 3 and the owning process. While a host is live, CLI and MCP clients exit 4 and name the owning pid and takeover hint. The TUI opens read-only with the same notice.

`--stdio` accepts one newline-delimited JSON request per line. The response echoes `id`, and stdout carries protocol lines only:

```json
{"v":1,"kind":"request","id":7,"command":"status","args":{"thread":null}}
{"v":1,"kind":"response","id":7,"ok":true,"result":{"scope":"host","threads":2,"running_turns":0}}
```

| Command | Result |
| --- | --- |
| `ping` | `{"pong":true}` |
| `claim-info` | The live claim row, or `null`. |
| `status` | `{"scope":"host" or "thread","threads":n,"running_turns":n}` |

A malformed line or unsupported version answers with `id: null` and code `malformed_line` or `bad_version`, and the host continues. An unknown command answers `not_implemented`. EOF stops the host and releases the claim.

The pipe's authority is its spawner, so `--stdio` requests need no grant. Over the local socket, every request except `ping` also carries `grant_id` and `secret`. The host accepts only the same uid, verifies the grant, and requires the `read` scope for `claim-info` and `status`. A missing grant answers `unauthenticated`, a refused grant answers `not_found`, `bad_secret`, `revoked`, or `expired`, and a granted command without the scope answers `not_permitted`. A different uid is closed with `peer_uid`. The socket is removed on shutdown.

`baton grant list` shows each grant's scopes, ceiling, expiry, state, and label, never its secret or hash. `baton grant renew <id> [--days N]` extends a live grant from now, keeps the later of the stored and requested instants, and leaves the secret file and hash untouched, so a connected client keeps working. It refuses a revoked grant and writes a `grant.renew` audit row. `baton grant revoke <id>` deletes the client secret file and refuses every later request with `revoked`. `baton audit list [--limit N] [--json]` shows the append-only audit log. Each event records the actor, environment, action, scope, confirmation, payload digest, result, timestamp, and retention. The table rejects updates and deletes, and a grant mint or revoke commits with its audit row in one transaction. Every accepted turn writes a `turn.submit` row in the same transaction as its message and turn rows; a refused or failed submission writes none, and the digest covers the thread, provider, model, and queue-drain flag, never the prompt text. MCP fork and queue clear also write audit rows, with the stdio spawner recorded as the confirming authority. At the host terminal, `pair [--label <name>] [--scope <s>]... [--expires-days N]` mints a grant with `read` and `operate` by default and prints a `baton://local#...` URL whose fragment carries the secret. `renew <id> [--days N]` extends one live grant from that terminal and works while the host holds the store. The URL is a credential, so keep it out of public logs. `baton attach --url <url> [--json]` sends one read-only `status` request over the socket and prints the host scope, thread count, and running turn count. It does not start a second engine or run recovery. The local socket and attach are available on macOS and Linux; Windows uses `baton serve --stdio`.

`baton host takeover --pid <pid>` prints the live claim's pid and process start and asks for a `y` or `yes` answer. Confirmation replaces the claim, fences the old host out, stops provider children recorded under the old host generation, settles all open turns and running orchestration, and releases the store for a new host. A wrong pid, changed claim, dead owner, held write lock, or declined prompt leaves the claim untouched. The old host process is not signalled.

## Turns and execution

```sh
baton exec -p <provider> [--effort level] [--json | --stream-json] "prompt"
baton exec -t <worker-thread> [--json] [--no-review] "answer"
baton spawn [-p provider] [--json] "task"
baton resume [-t id] [--fork] [--print] [--force]
baton fork [-t id] [--turn n] [--native] [--json] [title]
baton rewind [-t id] --turn N [--native] [--json]
```

`baton exec` runs one prompt and prints the result. `--stream-json` emits one JSON object per line, ending with a `type: "result"` row.

## Orchestration

```sh
baton orchestrate [--max-tasks N] [--plan-file path] [--plan-only] "goal"
baton orchestrate --list [--all] [--json]
baton orchestrate --run <run-id> [--json]
baton orchestrate --review <run-id> [--task N] [--json]
baton orchestrate --integrate <run-id> [--task N] [--json]
baton orchestrate --open-prs <run-id> [--task N] [--json]
baton orchestrate --archive <run-id> [--json]
baton runs settle <run-id> --status <status> [--force] [--json]
baton worktrees [--json] [--run <id>]
baton worktrees --clean [--force] [--run <id>]
```

`--max-tasks` accepts 1 to 16. `--integrate` merges approved worker branches. `--open-prs` pushes each approved branch and opens one pull request.

`baton runs settle` records a final status for a run that nothing is driving. Statuses are `completed`, `partial`, `failed`, `cancelled`, `needs_review`, and `needs_input`. `completed` is refused unless every task completed and no turn is open. Any other status closes open tasks and turns first. A run whose recorded owner is still alive needs `--force`.

## MCP

`baton mcp` serves the local store over MCP stdio.

```json
{
  "mcpServers": {
    "baton": {
      "command": "baton",
      "args": ["mcp"]
    }
  }
}
```

The server exposes 15 tools: `baton_doctor`, `baton_status`, `baton_threads`, `baton_turns`, `baton_agents`, `baton_messages`, `baton_queue`, `baton_search`, `baton_latest_diff`, `baton_processes`, `baton_orchestration_runs`, `baton_orchestration_report`, `baton_activity`, `baton_memories`, and `baton_fork`.

It is read-only except for `baton_queue` clear and `baton_fork`, which creates a new thread and leaves the source unchanged. The server reads the same database and honors `BATON_HOME`.
